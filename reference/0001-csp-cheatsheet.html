CSP cheat sheet

Directives, sources, fallback rules, and how to read a violation report. Built for lookup, not reading.

Anatomy

Content-Security-Policy: <directive> <source> <source>; <directive> <source>; …
  • Directives separated by ;, sources by spaces. Order is irrelevant.
  • Content-Security-Policy enforces. Content-Security-Policy-Report-Only only reports. Both can be sent at once.
  • Two enforcing policies on one response = both must allow a load (intersection), not union.

Directives you will meet

Forgetting that frame-ancestors and base-uri do not inherit from default-src is the single most common CSP mistake. A policy of default-src 'self' alone leaves your page embeddable by anyone.

The strict-CSP target

Recommended by web.dev, because host allowlists are bypassable in most real configurations:

Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';

Worked example: a typical multi-tenant SPA policy

Invented, but shaped like a real one you'll actually meet — a React SPA served by ASP.NET Core, pulling in a video embed, an analytics beacon, and a webfont host:

default-src 'self' *.example-app.com *.googleapis.com *.gstatic.com
            *.youtube.com cdn.example-assets.com blob: data: vjs.zencdn.net …
script-src 'self' *.example-app.com vjs.zencdn.net        ← plus the nonce, injected
style-src  'self' fonts.googleapis.com vjs.zencdn.net 'unsafe-inline'
frame-ancestors *.example-app.com *.example-app.co.uk
form-action 'self'
upgrade-insecure-requests
report-uri /api/csp-report

Notes to carry into later lessons:

  • No img-src, connect-src, or frame-src → all three fall back to that very wide default-src.
  • style-src keeps 'unsafe-inline': CSS-in-JS libraries (MUI/emotion, styled-components) inject styles at runtime, so a style nonce is not straightforward.
  • No object-src and no base-uri → both unrestricted. Cheap hardening win.
  • A host allowlist in script-src is precisely the shape web.dev calls bypassable.

A weaker sibling app, for comparison:

script-src 'self' 'unsafe-eval' 'unsafe-inline'

'unsafe-inline' in script-src means any injected <script> executes — much weaker than the policy above.

Reading a violation report

Every violation shows up in two shapes: a human-readable line in the DevTools console, and — if report-uri/report-to is set — a JSON csp-report object POSTed to your endpoint. Same event, two representations (MDN).

FieldMeaning
blocked-uriWhat was blocked. Truncated to scheme+host+port cross-origin (privacy).
disposition"enforce" (from Content-Security-Policy) or "report" (from -Report-Only).
effective-directiveThe directive that actually decided the block. Modern name.
violated-directiveHistoric name for the same value as effective-directive.
original-policyThe full header value in effect.
script-sampleFirst 40 chars of the inline content — only present when that directive carries 'report-sample'.
The trap: effective-directive can be more specific than anything you wrote. A policy with only style-src can report effective-directive: "style-src-elem" for a blocked <style> tag — Chrome and Firefox report the resource-type-specific name even though you never wrote that keyword.

Report-Only rollout

Content-Security-Policy-Report-Only never blocks — it only reports (MDN). Send it alongside the enforcing header; the browser evaluates each independently.

RuleConsequence
Both headers may be sent on one responseEnforcing decides what loads; report-only decides what gets reported.
Needs report-uri or report-toWithout one, "the operation won't have any effect" — a silent no-op.
Not supported in <meta>A rollout must happen in middleware / response headers.
blocked-uri is filled in either wayOnly disposition says whether anything was actually blocked.
  1. Keep the live policy enforcing. Put the tightened candidate in -Report-Only, with a report endpoint.
  2. Collect real traffic. Filter noise — browser extensions and malware generate reports you did not cause.
  3. Per violation, decide: widen the candidate (real dependency) or fix the app (self-host, add a nonce).
  4. Flip when the reports go quiet: candidate becomes Content-Security-Policy, report-only goes empty.

Debugging loop

  1. Reproduce with DevTools Console open — the error names the directive that blocked, and the blocked URL.
  2. Ask which resource type it was, then find that type's directive; if absent, the culprit is default-src.
  3. Add the narrowest source that fixes it. Never reach for 'unsafe-inline'/'unsafe-eval' as a first move.
  4. Before shipping a tightening, ship it as Content-Security-Policy-Report-Only and read the reports.
  5. Grade the result at csp-evaluator.withgoogle.com.

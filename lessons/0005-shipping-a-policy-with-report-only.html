Shipping a tighter policy with Report-Only

Lesson 5 · run the strict policy in a mode that can't break anything, read what it would have broken, then flip.

The win: you'll tighten a policy without an outage. Four moves in the lab: ship the strict policy in report-only mode, read the reports, fix, flip.

The 30-second version

  • Content-Security-Policy-Report-Only blocks nothing. It only reports.
  • You can send both headers on one response. The enforcing one decides what loads. The report-only one decides what gets reported. They don't talk to each other.
  • Report-only with no report-uri or report-to does nothing at all. MDN: "if not, the operation won't have any effect."
  • The two kinds of report look almost identical. disposition is the field that tells them apart: "enforce" means blocked, "report" means predicted.
  • It only works as a response header. No <meta> support — so a rollout lives in your middleware.

Why you need it

You can't tell what a strict policy breaks by reading it. The third-party widget, the analytics snippet, the font host someone added in 2023 — none of that is in the header. It's in the traffic.

So you let real page loads list the breakage for you. Fix first, flip second.

The trap: seeing report-only violations pile up and thinking production is broken. Nothing was blocked. Each report is a prediction of what would break if you flipped today. Check disposition first.

Hands-on: a rollout in four moves

cd D:\shared\OneDrive\Teach-Skill\CSP-Learn\sandbox
dotnet run --urls http://localhost:5099

Open http://localhost:5099 and keep the terminal in view — the server logs every report that hits /csp-report. appsettings.json is watched, so edits apply on refresh.

1 · Loose policy enforcing, strict candidate reporting

This is the shape of a real legacy app: what's live, plus what you'd like to ship. Replace both arrays in sandbox/appsettings.json:

"CSPHeaders": [
  "default-src 'self'",
  "script-src 'self' 'unsafe-eval' cdn.jsdelivr.net",
  "style-src 'self' 'unsafe-inline'",
  "img-src *",
  "connect-src *",
  "report-uri /csp-report"
],
"CSPReportOnlyHeaders": [
  "default-src 'self'",
  "script-src 'self'",
  "style-src 'self'",
  "img-src 'self'",
  "connect-src 'self'",
  "report-uri /csp-report"
]

Refresh. Every probe that passed before still passes. The candidate blocked nothing — that's the point.

2 · Read what the candidate would have killed

Guess before you look. Which probes should the candidate complain about?

  • Probe B — script from cdn.jsdelivr.net
  • Probe F — image from placehold.co
  • Probe G — fetch() to api.github.com

Now check the terminal. In each report, find "disposition": it says "report", not "enforce". That's your proof these came from the candidate. Match "effective-directive" to the list above.

3 · Fix from the evidence — but not all of it

Three violations, three different right answers. This is the judgement the lesson is for:

  • Probe G — the app genuinely needs that API. Widen the candidate: "connect-src 'self' api.github.com".
  • Probe B — a script host. You could allowlist it, but you have a nonce (lesson 3). Leave the candidate strict and fix the app instead: self-host the library, or load it with the nonce.
  • Probe F — your call. Decide, then say your reason out loud. Both answers are defensible.

Save, refresh, confirm the G report stops arriving. Shrinking reports are your progress bar.

4 · Flip

Move the candidate array into CSPHeaders, set "CSPReportOnlyHeaders": [], refresh.

Whatever you chose not to fix now goes BLOCKED for real, and its report comes back with "disposition": "enforce". Same violation, same directive — different consequence. That one field is the difference between a rollout and an outage.

Check yourself

A response carries both CSP headers. A script violates only the report-only one. What happens?

The headers are evaluated separately. Only the enforcing one can block. The report arrives with "disposition": "report".

You ship Content-Security-Policy-Report-Only: script-src 'self' and nothing else. After a week, no reports. Why?

MDN: a report directive "must be specified for reports to be sent: if not, the operation won't have any effect." Console errors still show up locally, which is why this failure hides so well.

Which field tells you whether a violation actually blocked something?

Both kinds of report fill in blocked-uri, so its name misleads. Only disposition separates them.

Recall — no scrolling up

Say these out loud, then open to check
  • What does Report-Only block? Nothing, ever. It only reports.
  • What must it carry to be worth shipping? report-uri or report-to.
  • Which field separates a real block from a prediction? disposition.
  • From lesson 4: which unsafe keyword survives next to a nonce? 'unsafe-eval' — a nonce only neutralizes 'unsafe-inline'.
  • From lesson 1: is default-src deny-by-default? No — it's a fallback for fetch directives you didn't write.

Read this before lesson 6

Primary source (10 minutes): MDN — Content-Security-Policy-Report-Only. Short page, and the source of both quiz gotchas above. Also read the report-to / Reporting-Endpoints example at the bottom — that's the modern replacement for the deprecated report-uri the lab uses.

One caveat from the field, per web.dev's strict-CSP guide: "When enabling CSP for production traffic, you might see some noise in the CSP violation reports from browser extensions and malware." Filter the garbage before you trust a report count.

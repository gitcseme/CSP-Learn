Telling a weak policy from a strict one at a glance

Lesson 4 · why 'unsafe-eval' and 'unsafe-inline' aren't the same kind of danger — and one of them, you already fixed.

The win: given script-src 'self' 'unsafe-eval' 'unsafe-inline', you'll be able to say exactly which keyword is doing the damage, prove it in the lab, and state the one-line migration — without reaching for "just remove unsafe-inline" as a reflex answer.

The 30-second version

  • 'unsafe-eval' lets any string run as code — eval(), new Function(), string timers. If an attacker can get a string into one of those, this keyword is the only thing stopping it. Nothing else neutralizes it.
  • 'unsafe-inline' lets any inline <script> run, attacker's or yours. But if the policy also carries a 'nonce-…' or 'sha256-…' source on script-src, modern browsers ignore 'unsafe-inline' entirely. It only still works for CSP1-only browsers you almost certainly don't need to support.
  • That's why your lab server already carries a real migration: every response gets a nonce (lesson 3), so 'unsafe-inline' in this policy would already be dead weight. 'unsafe-eval' would not be — nothing in the current setup touches it.

Two keywords, two different fixes

The migration for 'unsafe-inline' is: add a nonce or hash. Once you do, the keyword stops mattering to any browser your users actually run. You can drop it or leave it as CSP1 fallback — either is fine, and leaving it is common in the wild.

The migration for 'unsafe-eval' is: find what calls eval, and stop calling it. There is no nonce for eval. No source expression neutralizes it. If your bundler or a dependency genuinely needs it (older webpack dev builds, some templating engines), that's a real cost to budget, not a box to tick.

The trap this lesson is built to catch: seeing 'unsafe-inline' in a report and assuming it's the dangerous one just because it reads scarier. In a policy that already has a nonce, it's inert. Always check what else is on that directive before judging it.

Hands-on: prove both halves in the lab

cd D:\shared\OneDrive\Teach-Skill\CSP-Learn\sandbox
dotnet run --urls http://localhost:5099

Open http://localhost:5099. appsettings.json is watched — edits take effect on refresh, no restart needed.

Confirm the baseline

Refresh the page. Probe C (inline script, no nonce) and probe E (eval()) should both say BLOCKED. Neither keyword is in the current policy.

Add 'unsafe-eval' — watch it flip immediately

Open sandbox/appsettings.json. In CSPHeaders, change the script-src line to:

"script-src 'self' 'unsafe-eval' cdn.jsdelivr.net",

Save, refresh. Probe E should now say RAN / LOADED. That's the real, unguarded danger — any string reaching eval now executes, from anywhere in the app.

Add 'unsafe-inline' too — predict before you refresh

Change the same line to the mission's exact weak baseline, plus the allowlist host:

"script-src 'self' 'unsafe-eval' 'unsafe-inline' cdn.jsdelivr.net",

Before refreshing: will probe C flip to RAN / LOADED? Decide, then refresh and check.

Read why

Probe C is still BLOCKED. Look at <pre id="policy"> on the page — the actual header now reads something like:

script-src 'self' 'unsafe-eval' 'unsafe-inline' cdn.jsdelivr.net 'nonce-AbC123...'

The nonce is there because AppendNonce in Program.cs stamps it onto every script-src line automatically, no matter what you write in config. Its mere presence makes the browser disregard 'unsafe-inline' on this directive. You didn't have to remove the keyword — the nonce already did the job in lesson 3.

Put the policy back

Restore the script-src line to "script-src 'self' cdn.jsdelivr.net" and refresh, so the lab is clean for next time.

Check yourself

In script-src 'self' 'nonce-X' 'unsafe-inline', what does a modern browser do with 'unsafe-inline'?

A nonce or hash source on a directive makes browsers ignore 'unsafe-inline' on that same directive — this is exactly what kept probe C blocked in the lab even after adding the keyword.

Which keyword has no nonce/hash equivalent that can neutralize it?

Nonces and hashes target inline content — a tag's attribute or a hash of its bytes. eval() runs a runtime string, which has neither, so 'unsafe-eval' stays dangerous exactly as written until you remove it.

You inherit script-src 'self' 'nonce-…' 'unsafe-inline' 'unsafe-eval'. What's the single highest-value fix, given limited time?

'unsafe-inline' is already inert next to that nonce — removing it changes nothing for real users. 'unsafe-eval' is the live risk, and it's the one that takes actual work: finding the caller and removing the dependency on it.

Recall — no scrolling up

Say these out loud, then open to check
  • What neutralizes 'unsafe-inline'? A nonce or hash source on the same directive — modern browsers then ignore the keyword entirely.
  • What neutralizes 'unsafe-eval'? Nothing but removing it and whatever code calls eval/new Function.
  • What did the lab prove, concretely? Adding 'unsafe-eval' flipped probe E immediately; adding 'unsafe-inline' next to an auto-appended nonce changed nothing for probe C.

default-src is a fallback, not a deny

Lesson 6 · one directive can cover nine kinds of load and still say nothing at all about four others.

The win: given a policy that is mostly one big default-src, you'll name what it governs and what it leaves wide open — including the hole you can't see in a probe table.

The 30-second version

  • default-src is a fallback for fetch directives only. MDN: it "serves as a fallback for the other CSP fetch directives."
  • Name a directive yourself and the fallback stops for that one. MDN: "If there are other directives specified, default-src does not influence them."
  • Some directives never fall back — and when they're absent they restrict nothing. MDN's table for each of them reads: "No. Not setting this allows anything."
  • So default-src 'none' is not deny-everything. It denies fetches. Form targets, base URIs and framing are untouched.

Why this bites

A policy that looks total isn't. A long default-src feels like it covers the page, so nobody checks what's missing.

And what's missing produces no violation reports, because there's no directive to violate.

The trap: reading default-src as a default deny. It's a default value — handed only to fetch directives you didn't write.

The two halves of the directive list

Falls back to default-srcNever falls back
script-src, script-src-elem, script-src-attr, style-src, style-src-elem, style-src-attr, img-src, font-src, connect-src, media-src, object-src, manifest-src, frame-src, child-src, worker-src, prefetch-src base-uri, sandbox (document directives)
form-action, frame-ancestors (navigation directives)
report-to, report-uri (reporting)
upgrade-insecure-requests, trusted-types

The left column is one idea: fetching a resource. The right column is four other ideas, and they each need naming explicitly. Per MDN, document directives "govern the properties of a document or worker environment" and navigation directives "govern to which locations a user can navigate or submit a form."

Hands-on: find the hole in a giant default-src

cd D:\shared\OneDrive\Teach-Skill\CSP-Learn\sandbox
dotnet run --urls http://localhost:5099

Open http://localhost:5099. The lab has a new probe J: it injects a <base> tag after load, the way an XSS payload would, and reports whether the hijack worked. appsettings.json applies on refresh.

1 · One directive, nine probes

Replace CSPHeaders in sandbox/appsettings.json with a single permissive default-src — the shape you'll meet in a legacy app:

"CSPHeaders": [
  "default-src 'self' 'unsafe-inline' 'unsafe-eval' data: blob: cdn.jsdelivr.net placehold.co api.github.com",
  "report-uri /csp-report"
],
"CSPReportOnlyHeaders": []

Clearing CSPReportOnlyHeaders matters — your lesson 5 candidate is probably still in there, and it would double every report you see later.

Refresh. Probes A through I all pass, from one directive. That's the fallback doing nine jobs: script, style, image and connect all read their value from default-src.

2 · Name one directive and the fallback stops

Add one line, changing nothing else:

"img-src 'self'"

Refresh. Probe F goes BLOCKED — even though default-src still lists placehold.co. Once you write img-src, default-src stops applying to images completely. It does not merge, and it is not a floor.

3 · Find the hole

Look at probe J. It says RAN / LOADED — and here that's the bad news: the injected <base> took effect, so every relative URL on the page now points at an attacker's origin.

Your default-src lists nine sources and still permits this. base-uri is a document directive, so it never reads default-src, and MDN's line for it is exact: "Not setting this allows any URL."

Note what didn't happen: no violation report. Nothing was violated.

4 · Close it

Add one more line:

"base-uri 'none'"

Refresh. Probe J flips to BLOCKED, and now you do get a report — check the terminal for "effective-directive": "base-uri".

This is why web.dev's recommended strict CSP is script-src 'nonce-{RANDOM}' 'strict-dynamic'; object-src 'none'; base-uri 'none' — no default-src at all, and base-uri spelled out, because it "blocks the injection of <base> tags."

Check yourself

A policy is exactly default-src 'none' and nothing else. What may the page still do?

form-action is a navigation directive and never falls back, so an unset form-action allows anything. The other three are fetches, and 'none' stops them.

Your policy is default-src 'self'; img-src *. Where may images load from?

Naming img-src removes images from default-src's reach entirely. MDN: "If there are other directives specified, default-src does not influence them."

Which of these does default-src not act as a fallback for?

Three of these are fetch directives. form-action is a navigation directive — it governs where a form may submit, not what the page fetches.

Recall — no scrolling up

Say these out loud, then open to check
  • What kind of directive does default-src cover? Fetch directives, and only those.
  • Name two directives it can't cover. Any two of base-uri, sandbox, form-action, frame-ancestors.
  • What does an absent form-action permit? Anything — absent means unrestricted, not inherited.
  • From lesson 5: which field tells a real block from a prediction? disposition.
  • From lesson 3: why is a style-src nonce hard in a React app? CSS-in-JS libraries inject <style> tags from the browser, after your server is done.
  • From lesson 4: what makes a host allowlist in script-src weak? Any bypassable file on an allowed host becomes your script source.

Reading a CSP violation report

Lesson 2 · a policy blocks something in production. You will go from the report that lands on your server to the one-line fix — without guessing.

The win: given a CSP violation — a DevTools console line, or the JSON body your report-uri endpoint receives — you can name the exact directive that fired and write the smallest correct fix. You will also learn the one trap that makes people blame the wrong line in the policy.

The same event, two shapes

When the browser blocks a load, it tells you twice:

  • The console line — for a human, right now, in DevTools. Names the directive as written in the header, and (for a default-src fallback) adds an explanatory note.
  • The violation report — for a machine, POSTed as JSON to whatever report-uri (or the newer report-to) names, with Content-Type: application/csp-report (MDN).

The report body looks like this:

{
  "csp-report": {
    "document-uri": "https://example.com/app",
    "referrer": "",
    "violated-directive": "style-src-elem",
    "effective-directive": "style-src-elem",
    "original-policy": "default-src 'self'; style-src 'self' 'report-sample'; report-uri /csp-report",
    "disposition": "enforce",
    "blocked-uri": "inline",
    "status-code": 200,
    "script-sample": "#probe-h { outline-color: rgb(0"
  }
}
FieldMeaning
document-uriPage the violation happened on.
blocked-uriWhat got blocked. "inline" for inline script/style/attribute; truncated to scheme+host+port for a cross-origin URL.
disposition"enforce" if it came from an enforcing Content-Security-Policy header, "report" if from -Report-Only. The load still ran either way when "report".
effective-directiveThe directive that actually decided the block. This is the one to trust.
violated-directiveA historic name for the same value as effective-directive. Some older report consumers only have this field.
original-policyThe complete header value in force for that response.
script-sampleFirst 40 characters of the inline content — only appears when the relevant directive carries 'report-sample'. Omitted for external-file violations.

The trap: the report can name a directive you never wrote

Look again at the example above: the policy has style-src 'self' 'report-sample' — no style-src-elem anywhere. Yet effective-directive says "style-src-elem". CSP splits style-src into element-level and attribute-level cousins internally; when you write the umbrella directive, the browser still reports the specific one it resolved to. If you go looking in your header for the exact string the report names and don't find it, that's expected — search for the directive it's a specialisation of instead (style-src, script-src, …).

Read the script-sample field

Because style-src carries 'report-sample' in this lab's policy, probe H's report includes a script-sample — the first 40 characters of the blocked inline <style> block. Write the smallest correct fix — twice

Probe G is blocked because connect-src only allows 'self'.

  1. Add the narrowest fix: api.github.com to connect-src. Refresh — G passes, F and H are still blocked (you changed one directive, not the policy's shape).
  2. Now try the fix people reach for under time pressure: delete the connect-src line entirely. G still passes — but check the console for F. Has anything else changed? (No — img-src is still its own directive, so deleting connect-src only widens fetch to default-src's 'self', which happens to already cover it. This "worked," but it was luck: deleting a directive to fall back to default-src is only safe when you've checked what default-src actually allows.)

Put the explicit connect-src line back before moving on — an explicit allowlist beats an accidental one, even when both currently pass.

Check yourself

A report shows "effective-directive": "script-src-elem" but your policy only has script-src 'self'. What should you do?

script-src-elem is the element-specific cousin of script-src. When only the umbrella directive is set, the browser still names the specific one it resolved to in the report — the fix belongs on script-src.

A report has "disposition": "report" and "blocked-uri": "https://cdn.example.com". What actually happened in the browser?

disposition: "report" means this came from a Content-Security-Policy-Report-Only header — nothing is enforced, so the load succeeded. Only disposition: "enforce" means the resource was actually stopped.

Why does script-sample sometimes go missing from an otherwise identical violation report?

script-sample only appears when the directive that fired includes the 'report-sample' keyword — and only for inline script/style/attribute violations, never for a blocked external file. It is opt-in, not automatic, because the sampled text can itself be sensitive.

Recall — no scrolling up

Say these out loud, then open to check
  • What are the two shapes a single violation appears in? A human-readable DevTools console line, and (if configured) a JSON csp-report object POSTed to report-uri/report-to.
  • Which field should you trust to name the directive at fault? effective-directive — violated-directive is a historic alias with the same value.
  • What does disposition: "report" tell you that "enforce" doesn't? The resource still loaded — this violation came from a Report-Only header, not an enforcing one.
  • When does script-sample appear? Only when the directive that fired carries 'report-sample', and only for inline content, never an external file.

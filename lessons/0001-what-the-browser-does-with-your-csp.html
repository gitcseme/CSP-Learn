What the browser does with your CSP

Lesson 1 · you will read a policy, predict every block it causes, then watch a browser prove you right or wrong.

The win: by the end of this lesson you can look at a Content-Security-Policy header and say — for each resource on the page — allowed or blocked, and name the directive that decided it. That single skill is what turns a CSP violation from a mystery into a two-minute fix.

The model, in four sentences

A CSP is a list of directives, separated by ;. Each directive names a kind of resource and then lists the sources that are allowed for it (MDN). The browser applies it to every load the document attempts: scripts, styles, images, fonts, XHR/fetch, iframes, form posts. Nothing is allowed by omission — if a resource type has a directive that does not list a matching source, the load is blocked and an error appears in the console.

Content-Security-Policy: default-src 'self'; script-src 'self'; report-uri /csp-report
                         └────┬────┘ └─┬─┘  └────┬───┘        └──────┬──────┘
                          directive  source   directive           directive

The one rule people get wrong: default-src is a fallback, not a default

default-src only applies to resource types that have no directive of their own in this policy. The moment you write img-src, that directive takes over for images completely — default-src stops contributing anything to images, and your carefully listed sources in default-src no longer apply to them.

This is why a policy like the one in the cheat sheet's worked example behaves the way it does. Its default-src lists a long allowlist (*.youtube.com, cdn.example-assets.com, blob:, data:, …) and there is no img-src — so images fall back to that whole list. But there is a script-src, so scripts get only 'self' *.example-app.com vjs.zencdn.net, and nothing from the default-src list.

Sources you will actually meet

SourceMeans
'self'Same scheme + host + port as the document. Not "my whole company".
'none'Nothing at all. Only meaningful alone.
example.com, *.example-app.comHost allowlist. A wildcard covers subdomains, not the bare domain.
data:, blob:, wss:Whole schemes. Broad — data: in script-src is a hole.
'unsafe-inline'Allow inline <script>/<style> content. Turns off most of CSP's XSS value for that type.
'unsafe-eval'Allow eval(), new Function(), string setTimeout.
'nonce-{random}'Allow the inline scripts carrying this exact nonce attribute. Fresh value per response.
'sha256-{hash}'Allow inline content whose hash matches. Good for build-time-fixed inline scripts.

Full list, one page per directive: MDN's directive reference.

Hands-on: the lab

The workspace has a throwaway ASP.NET Core app in ./sandbox/. It builds its header the way a typical nonce-based CSP middleware does — random nonce per request, directives from appsettings.json, nonce appended to script-src — and serves one page with eight probes, each of which reports whether it ran or was blocked.

cd D:\Projects\claude\CSP-Learn\sandbox
dotnet run --urls http://localhost:5099

Open http://localhost:5099 with DevTools' Console open.

Predict before you look

The starting policy is:

default-src 'self'; script-src 'self'; report-uri /csp-report

Write down RAN or BLOCKED for each probe before scrolling the page. Guessing first is the point — the correction is what sticks.

ProbeYour call
A — external script, same origin 
B — external script, cdn.jsdelivr.net 
C — inline <script>, no nonce 
D — inline <script> with nonce 
E — eval() 
F — image from placehold.co 
G — fetch() to api.github.com 
H — inline <style> block 

Two of the eight run. Six are blocked. Which two?

Read the console, not just the table

Every blocked load logs a line naming the directive that refused it. Find the line for probe F and notice it blames default-src, not img-src — the fallback rule, visible in the wild.

Now make probe B pass — twice, two different ways

Edit sandbox/appsettings.json. The config is watched, so just save and refresh; no restart.

  1. The bad way: add 'unsafe-inline' to script-src. Does B pass? (No.) Which probe does it unblock instead, and what did you just give an attacker?
  2. The correct way: add cdn.jsdelivr.net to script-src.

The reflex this builds: a blocked resource is a source-list problem, not an 'unsafe-inline' problem.

Break the nonce

Probe D passes because the server put the same random value in both the header and the tag. Prove that is what is happening: view source, find nonce="…", compare with the Content-Security-Policy response header in the Network tab. They match. Refresh — both changed, together.

Now delete script-src from the policy entirely, leaving only default-src 'self'. Probe D now fails and the whole results table stops rendering. Why? Look at AppendNonce in sandbox/Program.cs: the nonce is only ever appended to a directive that starts with script-src. No script-src line, no nonce anywhere, and inline scripts fall back to default-src 'self', which does not permit inline content.

This is not a quirk of the lab — any middleware that appends a nonce only to script-src (a common, reasonable choice) behaves exactly this way the moment that line is removed from the policy.

Check yourself

Policy: default-src 'self' cdn.example.com; script-src 'self'. A page loads an image from cdn.example.com. What happens?

There is no img-src, so images fall back to default-src, which lists cdn.example.com. script-src governs scripts only — a directive never constrains a resource type it does not own.

Policy: script-src 'self' 'nonce-abc123'. Which script runs?

Nonces must match exactly, and they only apply to elements carrying a nonce attribute — inline onclick= handlers cannot carry one (they are governed by script-src-attr and need 'unsafe-hashes'). The CDN host is not listed.

Why is a nonce regenerated on every single response rather than cached per user session?

The nonce is a secret shared between your server and that one response. If an attacker can predict or read it (from an earlier page, a log, a cached response), their injected <script nonce="…"> is allowed to run and the policy has bought you nothing. Hence RandomNumberGenerator, 16 bytes, per request — see sandbox/Program.cs in this workspace's lab.

Recall — no scrolling up

Say these out loud, then open to check
  • When does default-src apply to images? Only when the policy has no img-src. If img-src exists, default-src contributes nothing to images.
  • What does 'self' match? The document's own scheme, host and port. Not subdomains, not other ports.
  • What must be true for an inline script to run under a nonce policy? The nonce attribute on the tag equals the 'nonce-…' source in the header of that same response.
  • Which two directives were added to the lab policy to unblock a CDN script — and which was wrong? script-src cdn.jsdelivr.net is right; 'unsafe-inline' unblocks a different probe and weakens the whole policy.

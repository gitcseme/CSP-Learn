Why script-src gets a nonce and style-src doesn't

Lesson 3 · same trick, two different levels of difficulty — and you'll wire one up by hand to feel why.

The win: you'll be able to explain, to another engineer, exactly why a nonce-based script-src is easy to ship but a nonce-based style-src usually isn't — in a React app using MUI, emotion, or styled-components. Then you'll fix it in the lab, so it's not just theory.

The 30-second version

  • A nonce proves one thing: "the server put this tag here on purpose."
  • Your server writes <script> tags itself, while building the page. Stamping a nonce on them is one line of template code.
  • CSS-in-JS libraries (MUI, emotion, styled-components) insert <style> tags from the browser, after the page has already loaded — long after your server's code has finished running.
  • That's the whole problem. The nonce has to travel from your server, across the network, into the browser, into the library's runtime, onto every style tag it creates. Four hops instead of one.
  • Given that cost, many teams just leave 'unsafe-inline' in style-src and accept the risk. Fixing it properly means wiring the nonce through — which is what you'll do in the lab.

One nonce, two very different jobs

Script tags: one code path. Your server prints the HTML. In the same breath, it prints the Content-Security-Policy header with 'nonce-X', and the <script nonce="X"> attribute on every inline script. Same request, same moment, same piece of code holding the value X. That's why it's simple.

Style tags from a library: four code paths.

  1. Your server generates the nonce and puts it in the header — same as before.
  2. Your server also has to hand that same value to the client-side JavaScript bundle somehow (an inline variable, a <meta> tag, a data attribute).
  3. Your React app has to read that value and pass it into the CSS-in-JS library's own configuration.
  4. The library has to actually use it — stamping the nonce onto every <style> tag it creates, forever, including ones created long after the page loaded.

Miss any one of those four steps and the styles are silently blocked. That's why it's hard, and why 'unsafe-inline' is the path of least resistance.

Hands-on: wire up a style nonce yourself

The lab has a new probe. Probe I inserts a <style> tag from JavaScript, after the page has loaded — exactly what MUI or emotion does under the hood.

dotnet run --urls http://localhost:5099

Open http://localhost:5099 with DevTools' Console open.

Confirm probe I is blocked

Look at the results table. Probe I should say BLOCKED. Check the console — the browser is refusing an inline style with no nonce and no 'unsafe-inline'.

Give the element a nonce — watch it still fail

Open sandbox/wwwroot/lab.html and find probe I's script. Uncomment this line:

injected.nonce = window.currentNonce;

Save, refresh. Still blocked. You did step 4 from the list above — but not step 1. The server never put a nonce in style-src at all, so there's nothing for the element's nonce to match.

Fix the server side

Open sandbox/Program.cs and find AppendNonce. It only recognises directives starting with script-src. Add style-src to that check, so the function appends the nonce there too.

Stop the app (Ctrl+C) and run it again — this is a C# change, not config, so it needs a restart. Refresh the page. Probe I should now say RAN / LOADED.

Name what you just did

You just performed, by hand, exactly what passing a nonce option into an Emotion cache does in a real React app: get the value from the header into the library, and get the library to stamp it on every style tag it creates (MUI's own CSP guide walks through the same steps with @emotion/cache).

Check yourself

Why is a script-src nonce simple but a style-src nonce hard, in one sentence?

Nonces themselves work identically for both. The difference is when the tag gets created — a server-rendered script tag exists at the same moment the header is written; a library-injected style tag is created later, client-side, so the nonce has to be carried across that gap.

You set element.nonce on a script-inserted style tag, but style-src has no nonce source. What happens?

A nonce on the element only helps if the header's style-src lists a matching 'nonce-…' source. Setting one side without the other changes nothing — this is exactly what you saw in the lab before editing AppendNonce.

Given the cost of wiring a style nonce through a CSS-in-JS library, what do many real teams do instead?

This is a real, common trade-off, not a mistake to be embarrassed about — inline style injection is a much smaller attack surface than inline script injection, so many teams accept 'unsafe-inline' here while keeping script-src strict.
